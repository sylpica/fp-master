# 追補：古いビルドの端末で「Importing a module script failed」（2026-11-06 発生）

## 事象
2026-11-06 12:17、iPhone で「問題データの読み込みに失敗しました：TypeError: Importing a module script failed.」と表示され使えなくなった（開き直しで復旧）。

## 機序（推定。端末内のキャッシュは遠隔確認できない）
- PWA は `registerType: 'prompt'`。新しい SW は「待機」し、利用者が「更新」を押すまで旧プリキャッシュの index.html・本体が返り続ける。
- 問題データのチャンク（g2_*/j2_*/explanations-* など）はプリキャッシュ対象外（ランタイムキャッシュ）。デプロイで旧ハッシュのファイルがサーバーから消え、端末のキャッシュにも無いと 404 で動的 import が失敗する。
- 従来の `importWithRetry` は同じ URL を再試行するだけで直らず、エラー画面には再読み込み手段が無かった。通常の再読み込みでも待機中の SW は有効化されない。

## 再現（e2e/stale-build.spec.ts）
旧ビルド（npm run build の dist）を配信 → SW インストール・1問解いて履歴を作る → 全ハッシュ付きファイル名を付け替えた「新ビルド」に差し替え（旧ファイルは消える）→ 旧状態で開く。
- 修正前：「問題データの読み込みに失敗しました：TypeError: Failed to fetch dynamically imported module: …/assets/g2_202405-aq-1CZ1m.js」で恒常的に失敗（再現成功。Chromium の文言。Safari の "Importing a module script failed" と同じ原因）。
- 修正後：自動で現行ビルドへ合流し、IndexedDB の履歴（1件）も保持。

## 修正
- `src/content/staleBuild.ts`：モジュール読み込み失敗の判定（Safari/Chromium/Firefox 文言）、SW の更新確認 → 待機中 SW の有効化（SKIP_WAITING）→ 1回だけ再読み込み。sessionStorage のガード（5分）でループを防ぎ、ガードを書けない場合・オフラインでは自動再読み込みしない。成功したらガード解除。
- `src/content/store.tsx`（問題データ）と `src/App.tsx`（遅延読み込みのページ）の両方で上記を適用。
- `src/ui/LoadErrorScreen.tsx`：エラー画面に「再読み込み」ボタン（同じ合流処理）と「学習履歴はこの端末に残っています。」を表示。ページ描画の例外用に ErrorBoundary を追加。UIルール4点に沿い、説明は最小限・本題（ボタン）を上、注記を下に配置、文字は折り返して切れない。
- 学習データ（IndexedDB）・キャッシュの全消去は行わない。

## ランタイムキャッシュ戦略（(d)）
変更しない。チャンクは内容ハッシュ付きで同一 URL の中身は不変、期限を付けるとオフラインで読めなくなるため。問題は「旧シェルが旧ハッシュを指す」ことで、キャッシュ期限では解決しない（キャッシュ名 'fp-question-data-v1' も据え置き）。
